# ExpenseFlow — Production Gap Audit

Honest assessment of what stands between this proof of concept and a production-ready service. Classification: **Blocking** (must fix before any real users/data touch it) or **Deferrable** (can ship without, with a documented risk). Effort estimates assume one engineer familiar with the codebase.

| Area | Gap | Classification | Effort |
|---|---|---|---|
| **Authentication & key rotation** | No authentication of any kind on any endpoint. Anyone who can reach the port can create, approve, or reject arbitrary expenses. The `ANTHROPIC_API_KEY` has no rotation mechanism — it's a static value in `.env`. | **Blocking** | 3–5 days for basic auth (API keys or OAuth2/OIDC) + role separation (submitter vs. approver); +1–2 days for a key rotation runbook/secret-manager integration. |
| **Input validation** | pydantic validates shape and basic constraints (`amount_minor > 0`, 3-letter currency) but does not validate `currency` against a real ISO-4217 list, does not bound `description`/`category` length, and does not sanitize free text. | **Blocking** (currency code) / **Deferrable** (length limits) | 1–2 days. |
| **Rate limiting** | None. `/reports/insights` calls an external paid API on every request with no throttling — a single misbehaving client could run up API cost or exhaust quota. | **Blocking** | 1 day to add per-IP/per-key rate limiting (e.g. `slowapi`) on the insights endpoint; 0.5 day elsewhere. |
| **Observability & logging** | Only ad hoc `logging.warning` calls in `app/insights.py`. No structured logging, no request IDs, no metrics, no tracing. Failures in the AI call are only visible in the uvicorn console. | **Blocking** | 2–3 days for structured logging + basic metrics (request count, latency, error rate) and shipping logs somewhere durable. |
| **Error handling** | Expense endpoints raise plain `HTTPException`s with minimal detail; there is no centralized exception handler, no consistent error envelope, and unexpected exceptions (e.g. a DB error) would surface as a raw 500 with a stack trace by default. | **Blocking** | 1–2 days for a global exception handler and a consistent error response shape. |
| **Database migrations & pooling** | Schema is created via `Base.metadata.create_all()` on startup — there is no migration tool (Alembic), so any schema change in production requires a manual, undocumented process. SQLite has no real connection pooling and does not scale to concurrent writers. | **Blocking** for any multi-instance or schema-evolving deployment | 3–4 days: introduce Alembic, migrate to Postgres, configure pooling. |
| **Secrets management** | `ANTHROPIC_API_KEY` lives in a local `.env` file, gitignored but otherwise unmanaged: no encryption at rest, no access audit, no rotation. | **Blocking** for any shared/hosted deployment | 1–2 days to move to a secrets manager (e.g. cloud KMS/secrets store) and inject via environment at deploy time. |
| **Tests & coverage** | `pytest` is installed and referenced in `CLAUDE.md`, but no test suite exists yet. Every validation so far has been manual (Swagger UI, curl, the browser). | **Blocking** | 3–5 days for a baseline suite: unit tests for `app/insights.py`'s JSON-parsing/fallback logic, integration tests for the CRUD + approval endpoints, and a smoke test for `/health`. |
| **Deployment & health checks** | `GET /health` exists and reports DB reachability via row count, but there is no containerization, no readiness vs. liveness distinction, no graceful shutdown handling, and no deployment pipeline (CI/CD). | **Deferrable** for a single-instance demo, **Blocking** for real deployment | 2–3 days for a Dockerfile, CI pipeline, and basic readiness/liveness separation. |
| **Data privacy (expense data)** | Expense records may contain sensitive information (who spent what, where, on what) with no access control, no encryption at rest, no audit trail of who approved/rejected what, and no data retention or deletion policy. | **Blocking** for any real financial or PII-adjacent data | 3–5 days for access control (ties to Authentication above) + audit logging; policy definition is a business decision, not just engineering. |

## Bottom line

The PoC demonstrates the full user journey (submit → list → approve/reject → AI insight) and is a solid basis for the data model and API shape. But the total remaining engineering effort above — roughly **20–30 engineer-days** — is several times larger than the PoC itself, concentrated in authentication, observability, data durability (Postgres + migrations), and testing. None of the blocking items are exotic; they are the standard bar any internal financial-adjacent tool needs to clear before real users or real money touch it.

**Recommendation:** greenlight-with-conditions — proceed to a production build, but treat Authentication, Database migrations/pooling, and Tests & coverage as prerequisites for the first real deployment, not follow-up work.
